# 未知患者姿态条件下的受力驱动轨迹：实现边界

最终决定与实现：用户已选择优先实际康复条件，正式主线采用机械臂位姿/受力驱动的 TCP 候选决策，原六参数只作离线对照。scripts/tcp_force_training.py 和 lab_session.py 已接通该主线，完整操作见 [TCP_FORCE_EXPERIMENT.md](TCP_FORCE_EXPERIMENT.md)。下文保留作取舍依据，原“尚需取舍”状态已由此决定替代。

更新：2026-11-12。用户进一步明确：实际康复中不能精确规定患者姿态，髋中心、连接偏移和有效长度也不能作为已知输入；轨迹应根据机械臂感受到的力调整。这个条件取代此前“已标定固定几何”的部署前提。

## 当前代码能证明什么

现有 robot_observation.py 调用原逆运动学和 JᵀF，把机械臂实测 TCP 与受力转换成模型姿态和广义力矩。它依赖髋中心、有效长度、连接偏移、平面及点力条件，因此只是一条有条件的观测适配，不能作为当前实际条件下的正式方案。

假腿传感器不进入训练的边界仍正确。此前离线测试证明该条件适配不读取假腿数据，不能证明患者几何未知时也能辨识六参数。默认缺少标定会被阻止，不应为通过检查而随意填入名义值或删除检查。

原核心依赖可在源码直接核对：

| 来源 | 依赖 |
| --- | --- |
| experiment_algorithm/coupled_model.py 的 STATE_COLUMNS | 髋膝 q、dq、ddq |
| experiment_algorithm/coordinate_consistent_model.py 的 design_matrix | 以关节运动构建六参数力学回归矩阵 |
| experiment_algorithm/surrogate.py 的 _accepted/_fit_physics | 两关节广义力矩观测及上述回归矩阵 |
| measurement_validation/robot_observation.py | 通过已知几何 IK/JᵀF 构造这些观测 |
| experiment_algorithm/surrogate.py 的 ModelContext | 名义关节候选、物理基线及原关节力矩端点 |

在当前模型和这些未知条件下，不能保证从末端受力唯一拆分质量尺度、髋/膝刚度、髋/膝阻尼和耦合刚度。姿态、力臂、接触及力学特性会共同影响末端响应。六维力/力矩的六个通道不等于六个参数可辨识。

## 与实际目标匹配的观测和决策

可用的在线信息应限定为机械臂实际位姿、运动速度、六维受力及其时间记录。患者真实姿态和假腿传感器不作为必需输入。机器人自身 TCP、力坐标、工具/负载补偿和时间质量仍需校验；这与精确掌握患者几何是不同的问题。

与该目标相符的主线是：给定康复任务的 TCP 方向/行程/持续时间等要求 → 执行轨迹 → 记录机械臂运动和受力 → 评价是否完成任务及受力表现 → 决定下一条 TCP 轨迹。

只把“力更小”作为目标会偏向停止、减小行程或解除有效牵引，不能据此认定康复运动完成。测到受力并不能唯一确定患者需要怎样的康复轨迹，任务目标仍需明确。轮间轨迹选择和同一轮内实时力反馈控制是不同的实现，不应混称已完成。

## 为什么不能直接把现有开关打开

原代码虽然有 PURE_BO 分支，但当前 ModelContext、观测结构、E3/E2/peak_ratio 与候选特征仍建立在原关节模型和候选上。它不是一个已经完成的、患者几何无关的力驱动 TCP 接口。

若选择直接优化机器人受力，需要重新明确：TCP 候选参数的含义、直接可测的受力评价、任务完成约束、预测与验证方法。可以评估保留已有 GP/约束决策代码，但必须按最终定义审核；不能把直接受力目标仍标为原 E 指标，也不能把末端响应参数改名为原六参数而宣称算法未变。

## 已评估的取舍

曾评估两项选择，用户已选择第1项：

1. 优先满足实际康复信息条件，正式方法改为机械臂观测驱动的 TCP 决策；原六参数方法作为有条件的离线对照。
2. 保留原六参数物理含义，先研究未知几何下的可辨识性与最少可用信息，不将现有几何适配作为部署方案。

已按第1项实现直接受力指标和 TCP 候选接口，复用已有 GP/EI/可行性工具。原六参数含义和核心保持不变，仅作离线对照。这个用户确认的主方法变更替代了此前“原算法完全不变地部署”的要求，没有运行真机。
